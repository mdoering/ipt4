# IPT4 M5 (Admin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An administrator can do on IPT4 everything IPT 3's `/admin` area offers: configuration, UI management (colours, logo), logs, user accounts, extensions, vocabularies, data package schemas, organisations, IPT registration (against a stub registry; GBIF UAT is M6), bulk publication with its status page and API, and deleting a published version.

**Architecture:**
- Same pattern as M3/M4: `tools/port/port-action.py` ports each `org.gbif.ipt.action.admin.*Action` to a page bean in `org.gbif.ipt.web.admin`; `AdminPageController`s map IPT 3's `/admin/<action>` and `/admin-api/<action>` URLs (with and without `.do`) and results. Admin global results as IPT 3 (`cancel` → `redirect:/home.do`); access is the `SecurityFilterChain`'s ADMIN rule (already there), including `bulkReport`, which IPT 3 ran without a check.
- **Form objects of shared types.** IPT 3 bound `user.*` (depth 1), `organisation.*` (depth 2) and `ipt.*`/`organisation.*` (depth 3, registration) onto the live objects the managers hold. IPT4 binds them only on pages that declare them as form objects (`ActionPage.formObjects()`: property name → allowed sub-paths, taken from the templates' field names), and only onto a working copy (a new instance or a clone); the manager's save puts the copy in place. The SHARED rule stays for every other page and path.
- **Registry in tests.** A `StubRegistry` (JDK `HttpServer`) serves captured registry JSON (`/registry/extensions.json`, `/registry/dataPackages.json`, `/registry/organisation.json`, `/registry/organisation/<key>.json`, `/registry/ipt/register`, `/registry/ipt/update/<key>`) and the extension/vocabulary/schema files those list (from `installed-config`), with URLs rewritten to itself. `dev.registrydev.url` points at it per test class. One `@Tag("network")` test installs and updates an extension and a schema from the real registry and rs.gbif.org (excluded by default, run once for the exit).

**Tech Stack:** as M4.

**Spec:** `docs/design.md` §4 (controllers, security, uploads, downloads) and milestone M5.

## Global Constraints

- IPT 3 URLs keep working with and without `.do` and with the same parameters.
- Templates converted with `tools/ftl-migrate`; manual edits only where the report or CSRF needs them.
- CSRF on every POST; no state change on GET (`deleteVersion` and any other admin GET mutator become POSTs; their portal links send POSTs).
- No network access in tests except `@Tag("network")`.
- Secrets (SMTP password, organisation passwords, IPT registration password) are never rendered back in HTML and stay encrypted at rest; an empty password field keeps the stored one where IPT 3 did.
- Binding rules from M3/M4 stay; shared types only as declared form objects on working copies.

## Review Focus

1. **Admin only.** Every `/admin/**` and `/admin-api/**` handler refuses anonymous users (login), users and managers (401), with and without CSRF. Test: Task 1 `AdminAuthorizationMatrixTest` (all mappings from `RequestMappingHandlerMapping`).
2. **Rejected forms change nothing.** An invalid user, organisation, configuration or registration form leaves the live objects and files as they were. Test: Task 3 `rejectedUserFormChangesNothing`, Task 5 `rejectedOrganisationFormChangesNothing`.
3. **Lock-out.** The last administrator cannot be deleted or demoted; an admin cannot delete themself; a user losing the admin role loses admin access on the next request. Test: Task 3 `lastAdminIsKept`, `demotedAdminLosesAccess`.
4. **Files.** The log download serves only `debug.log`/`admin.log` from the logs folder (`log=../config/users`, absolute paths, encoded dots refused); the app logo upload accepts images only and ignores hostile names. Test: Task 2 `logfileStaysInLogsFolder`, `appLogoUpload`.
5. **Installed vocabularies.** Deleting an extension or schema used by a mapping is refused with IPT 3's message; an update keeps mappings working; installing from a URL needs http(s). Test: Task 4 `extensionInUseIsKept`, `updateKeepsMappings`.

### Task 1: Admin templates and framework

- Convert `admin/*.ftl` (except the setup steps, done in M2) with `tools/ftl-migrate`; fix the report's manual items.
- Raw port of all admin actions with `port-action.py`; `AdminHomePage` (`/admin/`, `/admin/home`); admin result map; `ActionPage.formObjects()` in `ActionRunner` (declared shared-type properties bind only below their allowed sub-paths, on the page's working copy).
- Tests: templates parse; `AdminAuthorizationMatrixTest`; `ActionRunnerTest` cases for form objects (allowed sub-path binds, undeclared sub-path refused, other pages still refuse); admin home renders for an admin.

### Task 2: Configuration, UI management, logs

- `ConfigAction` (`config`): base URL change with IPT 3's checks and messages (malformed, localhost warning, unreachable), proxy, debug, archival mode/limit, default locale, analytics key, admin email, SMTP settings (password kept when left empty, encrypted), coordinates, logo redirect URL; written to `ipt.properties`.
- `UIManagementAction` (`uiManagement`, `appLogoUpload`): colour scheme, app logo upload and removal; `appLogo` served (already ported in M2: check).
- `LogsAction` (`logs`, `logfile?log=`).
- Tests: config round trip (GET + unchanged POST keeps `ipt.properties`), invalid base URL message, SMTP password not rendered; colour change shows in the theme CSS variables; `appLogoUpload`; `logfileStaysInLogsFolder`.

### Task 3: User accounts

- `UserAccountsAction` (`users`, `user` GET/POST/delete, reset password) with `user` as a form object (email, firstname, lastname, role, password; password2/resetPassword top-level).
- Tests: create, edit, reset password (message shows the new password as IPT 3), delete; validation messages (email format, duplicate, password rules); `rejectedUserFormChangesNothing`; `lastAdminIsKept`; `demotedAdminLosesAccess`; deleting a user who is the last manager of a resource gives IPT 3's message.

### Task 4: Extensions, vocabularies, data package schemas

- `ExtensionsAction` (`extensions`, `extension` GET/install/delete, `updateExtension`, synchronise vocabularies), `VocabulariesAction` (`vocabulary` page; the popup part exists from M3), `DataPackageSchemaAction` (`dataPackages`, `dataPackage`, `updateDataPackage`).
- `StubRegistry` test support.
- Tests: list shows installed and available extensions from the stub; install an extension and its vocabularies; update to a newer version (stub serves two versions) keeps mappings; `extensionInUseIsKept`; delete unused; schema install/update/delete the same way; vocabulary page; `@Tag("network")` install/update from rs.gbif.org.

### Task 5: Organisations and IPT registration

- `OrganisationsAction` (`organisations`, `organisationsSynchronize`, `organisation` add/edit/delete) with `organisation` as a form object; `RegistrationAction` (`registration`, `updateRegistration`, `changeTokens`, `associateWithNetwork`) with `ipt` and `organisation` form objects.
- Tests against the stub: add an organisation with its password (validated by the stub's login), edit, delete (refused when resources use it), synchronise; `rejectedOrganisationFormChangesNothing`; organisation and IPT passwords not rendered and encrypted in `registration.json`; register the IPT (stub records the request body; IPT 3's form fields); update registration; change tokens.

### Task 6: Bulk publication, status, delete version

- `BulkPublicationAction` (`bulk-publication`), `PublishAllResourcesAction` (`publishAll`), `PublishingStatusAction` (`bulkReport`), `PublishingStatusApiAction` (`admin-api/publication-report(s)`), `DeleteVersionAction` (`deleteVersion`, POST; portal links send POSTs).
- Tests: publish two resources in bulk, status page and JSON (IPT 3's shapes: `StatusReport` fields), excluded resources skipped; delete a version (files gone, history updated) only by POST; GET refused.

### Task 7: M5 exit checks

- Crawler follows `/admin/` (drop it from `NOT_YET`); authorization matrix; full verify; Docker smoke; the admin checklist below, each item pointing to its test:
  configuration saved, base URL changed, UI colours and logo, logs viewed and downloaded, user created/edited/deleted, extension and schema installed/updated/deleted, organisation added, IPT registered (stub), bulk publication, version deleted.
